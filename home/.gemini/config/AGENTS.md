# グローバル開発憲法（個人開発・高スループット運用）

## コミュニケーション
- 原則として日本語で簡潔に応答する。
- 事実・実測結果と推測を明確に分ける。未実行のテストや確認していない挙動を「通るはず」と断定しない。

## ブランチ・PR 設計（小粒・並列・高スループット）
- **1 PR 1 関心事**: 機能追加・リファクタ・バグ修正を混ぜず、数分でレビュー・判断できる小粒な PR に分割する。
- **デフォルトブランチ保護**: `main` / `master` への直接コミット・直接 push は禁止。必ず作業用の feature ブランチまたは git worktree を切って作業する。
- **並列化の徹底**: 独立した複数タスクや広い調査はサブエージェント・並列 worktree を活用し、コンテキスト肥大化や巨大な単一 PR を避ける。
- **feature ブランチの自律進行**: 実装・テスト・lint・コミット・feature ブランチへの `git push`・`gh pr create` まで自律的に完遂してよい。
- **人間承認ゲート**: `gh pr merge`、リポジトリ削除、リリース作成、パッケージ・イメージ公開は必ずユーザーの明示的な承認を得る。

## 品質・検証ゲート
- PR 作成および完了報告の前に、対象リポジトリのテスト・lint・型チェックを実行し、実際の終了コードと結果を確認する。
- 既存テストが壊れたまま PR を作らない。環境都合で実行できない検証項目がある場合は、実行できなかった理由と範囲を明記する。
- バグ修正や機能追加では、可能な限り先に失敗するテストを書いてから実装する（TDD）。

## コミット・PR 衛生
- コミットメッセージはリポジトリ規約（Conventional Commits 等）に従い、意図が 1 行で伝わるようにする。
- コミットメッセージに `Co-Authored-By` トレーラーを付与しない。
- PR 本文は以下を簡潔にまとめる:
  - **What**: 何を変えたか
  - **Why**: なぜ必要か
  - **Verification**: 実行した検証コマンドと結果
- 関係ない未コミット変更や一時ファイルを巻き込まない。`git add -A` / `git add .` ではなく対象ファイルを明示してステージする。

## セキュリティ・機密保護
- `.env`（`.env.sample` 等のテンプレートを除く）・秘密鍵・認証情報（`~/.ssh`, `~/.aws`, `~/.gnupg`, `credentials.json`, `*.pem`, `*.key` 等）を読み取り・出力・コミットしない。
- 外部エンドポイントへのデータ送信（`curl -d` / `POST` 等）や破壊的コマンド（`git push --force`, `git reset --hard`, `rm -rf` の広範囲適用）は実行しない。
